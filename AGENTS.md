# Правила разработки «Числа»

Эти правила обязательны для изменений в этом репозитории. Если они расходятся с инструкциями среды выполнения, приоритет у инструкций среды.

## Релиз и контроль версии

- Единственный источник номера релиза приложения — `version` в `package.json`; синхронизировать `package-lock.json` командой `npm version <номер> --no-git-tag-version`. Не писать номер вручную в JSX, CSS или документации как актуальный.
- **Каждый набор изменений, публикуемый для пользователя через `main`, должен получать новый номер версии.** Для исправления — patch, для новой обратно совместимой функции — minor, для несовместимого изменения — major. Если в одной ветке несколько коммитов до одной публикации, достаточно одного повышения версии перед слиянием. Не повторно использовать уже опубликованный номер.
- На сайте номер текущего пакета должен постоянно присутствовать вверху бокового меню/гамбургера, быть читаемым на телефоне сразу после открытия (без прокрутки), и браться из `package.json`. В «Родителям» допускается дублирование того же номера.
- Перед слиянием проверять, что версия в меню соответствует `package.json`, что мобильное меню раскрывается и что номер виден при ширине 320–390 px. Положительный HTTP-ответ сервера **не доказывает**, что пользователь видит новую сборку: при расхождении сообщать номер видимой версии и проверять публикацию и PWA-кеш.

## Изменения интерфейса и учебного содержания

- **Конфликт или иная блокирующая причина — вопрос владельцу (ASK-01).** Остановить спорную часть, показать конфликт и 2–3 варианта с последствиями, дождаться решения, записать его в `docs/PRODUCT_RULES.md` с датой. Обходить правило или ослаблять тест ради зелёного прогона нельзя.
- **Новый урок и переделка объяснения — по [стандарту урока](docs/LESSON_STANDARD.md):** ровно 3 шага с действием ребёнка на каждом, не менее двух игр разных механик, бюджеты текста и контраста из стандарта, отдельная проверка только из утверждённых заданий. Измеряемые пороги проверяются тестами или измерениями; отсутствующие проверки добавляются при разработке. Игры выбираются по учебной цели, а не ради новизны; перенос обязателен только для механик переноса, с альтернативой нажатием и клавиатурой. Практический маршрут — [подготовка урока](docs/LESSON_WORKFLOW.md).

- Проверять затронутые экраны на маленьком телефоне и iPad в портретной ориентации, доступность управления с клавиатуры/скринридера и `prefers-reduced-motion` для анимаций. Для задания с цифровой клавиатурой при 768×1024 и 820×1180 изображение, поле, клавиатура и кнопка проверки должны помещаться без вертикальной прокрутки с запасом не менее 48 CSS px; кнопки клавиатуры — не ниже 44 CSS px. Не обрезать длинные задания ради этого требования: если содержание не помещается, оставлять безопасную прокрутку. Не размещать номиналы поверх фактурных изображений; числа и подписи должны читаться отдельно.
- На телефонах иллюстрированные карточки сортировки размещать по одной в строке: крупная предметная картинка занимает левую часть карточки по её высоте, значение/подпись — справа от картинки, вертикальные стрелки — справа от подписи. Не уменьшать изображение до миниатюры над текстом. На достаточно широких экранах допустим один горизонтальный ряд с горизонтальными стрелками; оставлять стрелки видимыми и сохранять перетаскивание. Проверять все виды таких карточек (массы, грузы, календарь), не обрезать содержимое ради отсутствия прокрутки.
- Иллюстрация задачи показывает только данные условия, не раскрывает искомый ответ. Различать дизайн разных единиц массы; не утверждать, что пустой ящик, контейнер или любой спортсмен весит ровно 100 кг.
- Сведения об учебнике и охвате курса держать в разделе «Родителям», а не на детских карточках. Наблюдения за детьми не подменять результатами автоматических тестов.

## Охват учебников

- **COVERAGE-01:** каждый согласованный учебник должен быть полностью покрыт теорией и заданиями; вести отдельный постраничный учёт материалов, номеров упражнений и их частей по [инструкции](docs/TEXTBOOK_COVERAGE.md). Обновлять `coverage-data/textbooks.json` и отчёт `npm run coverage:report`, проверять `npm run coverage:check`. Не считать неизвестные страницы, авторские дополнения или ссылку темы покрытием. Автоматическая проверка не заменяет ручную сверку PDF и не снимает ограничений источника и PILOT-01.

## Проверка и публикация

- Перед публикацией выполнять `npm ci`, `npm run format:check`, `npm run check` и затронутые e2e-тесты (при изменении общего интерфейса — весь `npm run test:e2e`). При изменении версии обязательно тестировать видимость номера в мобильном гамбургер-меню.
- **CI-01:** полный набор браузерных проверок обязателен перед слиянием; части CI в совокупности должны покрывать каждый тест ровно один раз. Публикация `main` разрешена только после всех успешных проверок и использует ту же сборку, что проверялась; не публиковать устаревший коммит. Порядок и локальные быстрые команды — в [CI_PIPELINE.md](docs/CI_PIPELINE.md).
- В отчёте разделять реализованное, опубликованное в PR и уже слитое в `main`; не выдавать открытую ветку или запущенный предпросмотр за обновлённый сайт пользователя.

## Проверяемые правила продукта

- [Манифест и стандарт работы](docs/DEVELOPMENT_STANDARD.md) применять к задачам, макетам и PR совместно с [реестром правил и статусов](docs/PRODUCT_RULES.md). Амбициозные цели не выдавать за достигнутые; экспериментальные эффекты (звук, конфетти, shake) не включать без проверки доступности и согласования. Реестр обязателен. Владелец может изменить, временно приостановить или отменить правило через чат/PR. Не делать исключений молча: при конфликте назвать правила, предложить безопасный вариант и спросить владельца.
- Номер страницы в теме не доказывает происхождение каждого задания. Скрывать неподтверждённые задания; основа доступных заданий требует сверки конкретных условий с утверждённым первоисточником; авторские дополнения допускаются только после отдельного согласования владельцем каждого условия и ответа, с явной пометкой происхождения. Не использовать найденный в сети учебник до согласования точного издания владельцем.
- Объяснять визуально до проверки; предоставлять отдельное обучение и проверку. Изображение должно буквально соответствовать словам. Завершение урока — короткий вывод и главное действие; следующие непройденные темы заметнее уже пройденных; мобильный выбор класса подписан словами.
- Для фото учебника записывать издание, страницу и конкретное упражнение в `docs/SOURCE_AUDIT.md`; изменённые числа, новые сюжеты, примеры по таблице и темы только из оглавления не считать заданиями книги; не открывать их детям как проверку без отдельного согласования авторского дополнения. В `src/content/approved.ts` привязывать видимое задание к этим данным и фиксировать его подпись, чтобы редактирование не открыло непроверенный вариант. Не удалять скрытый архив или прогресс; закрыть каталог, рекомендации, импорт и восстановление старой сессии. Исторические браузерные тесты скрытого банка хранить отдельно от CI, новые тесты проверяют настоящий доступный банк.

## От миссии к реализации

- Новые решения выводить из [миссии и исследовательской концепции](docs/LEARNING_VISION.md) через [реестр правил](docs/PRODUCT_RULES.md). Если развлекательный эффект спорит с проверенным содержанием или доступностью — остановиться и спросить владельца, предложив содержательный вариант.
- Перед масштабированием новой механики проверить один предметный пилот: источник → учебная цель → понятная сцена → самостоятельное действие → подтверждённая проверка → автотесты → наблюдение ребёнка. Не выдавать автоматические тесты за детский пилот.
